# Password-login resource protection

Security review identified unbounded scrypt work for random, disabled and locked usernames, performed inside a transaction using the same pool as live session authorization. The correction stays on the feature branch; password login remains disabled in the deployment configuration.

Every syntactically valid password request passes a fixed local gate and then one atomic shared PostgreSQL admission update before any account lookup or KDF. Each process permits one in-flight attempt, without a waiting queue, and at most 48 requests/minute to the admission database. The singleton shared row permits 12 admitted attempts/minute and one active renewable lease across processes, regardless of username or supplied IP headers. Random usernames cannot allocate unlimited limiter rows or bypass the shared budget.

An admitted unknown, disabled, locked or malformed-hash account performs the same fixed scrypt parameters as an admitted ordinary account, then returns the same generic sign-in failure. Rejected admission never looks up an account or performs a KDF. The comparison uses timing-safe equality; dummy work can never authorize an account. No hardcoded credential or account exists.

Password queries use a separate one-connection pool with 1.5-second statement and 150ms lock deadlines. Existing session authorization uses its separate two-connection pool. No transaction or account-row lock remains open during hashing. Success and failure writes recheck current password/version/role/disabled/lock state and admission ownership. The lease renews every 15 seconds and has two-minute crash recovery; lost ownership cannot authorize, and a stale release cannot clear a replacement owner's lease. A failed release stays closed until expiry. Missing admission schema/state rejects password login before hashing.

Apply candidate migrations `0001_admin_accounts.sql` and `0002_password_admission.sql` to the approved branch before enabling `ADMIN_PASSWORD_LOGIN`. The explicit provisioning command applies both idempotently; HTTP requests never create tables, accounts or grants. Migration replay does not reset live quota/lease state. Keep Netlify preview and production databases isolated.

`pnpm test:auth` uses actual isolated PostgreSQL and Auth.js browser login, then tests four processes submitting 256 parallel random-name, locked-account and disabled-account requests per scenario. It asserts non-overlapping KDF intervals, shared budget accounting, zero password transactions held during KDF and actual authenticated API availability. Further checks cover a same-process burst with concurrent session authorization, quota expiry, missing schema, abandoned leases, lost ownership and stale release. Private test backups, random passwords, processes and containers are removed afterward. Exact measurements are in `evidence/backup-auth-results.json`.

These application checks do not certify production ingress, function concurrency or database capacity. Sustained hostile traffic can exhaust the password-login budget; existing sessions and identity-provider sign-in do not consume it. Approved Netlify integration and capacity checks remain required before enabling production password login. No paid service, external rate-limit grant, permanent credential or public deployment was created by this correction.

Primary references: [Node scrypt](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback), [PostgreSQL atomic UPDATE/RETURNING](https://www.postgresql.org/docs/current/sql-update.html).

## One coherent Git / SSR / database architecture

GitHub's versioned content JSON is the sole published-content source and draft history. SSR reads the deployed JSON; public pages need no runtime Git token or database. Auth, preview and content writes use the same server authorization path. Local tests share the production Zod schema and exercise a real isolated Git repository and Postgres database.

The optional database holds administrator identities, rate locks and session versions. Existing Git drafts already provide durable preview/history; adding a duplicate content store is unnecessary. Netlify Database's current official SDK selects the appropriate deploy branch through `getConnectionString()`. Set `ADMIN_DATABASE_PROVIDER=netlify` only after inspecting and approving the existing project's database. External approved Postgres remains available via `AUTH_DATABASE_URL`; do not share production credentials with previews.

Netlify Database requires a credit-based plan and incurs usage credits. No cloud database has been provisioned or inspected without authenticated project access. Candidate additive migration `database/migrations/0001_admin_accounts.sql` stays outside Netlify's automatic migration directory until target approval. After approval, use the project's chosen migration workflow; the native directory is `netlify/database/migrations`. Do not enable both native and separate migrations for the same schema. HTTP requests never create tables or accounts.

`pnpm test:auth` creates a random-password PostgreSQL 17 container on loopback, applies the migration twice, authenticates through the real browser form, takes a private `pg_dump`, restores into another isolated database, verifies the restored account/version and removes the container and all temporary secrets. For cloud operation, arrange private encrypted backups and a restore rehearsal on an isolated branch; Git retains content versions separately.
